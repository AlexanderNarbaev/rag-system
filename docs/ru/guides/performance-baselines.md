# Базовые показатели производительности

Этот документ устанавливает базовые задержки для каждого ключевого компонента конвейера RAG-системы. Эти baselines служат gates регрессии — любой p95, превышающий заявленный порог, указывает на регрессию производительности, которую нужно исследовать до merge.

## Запуск бенчмарков

```bash
# Запустить все бенчмарки задержки
python scripts/run_benchmarks.py

# Запустить конкретную категорию
python scripts/run_benchmarks.py --category retrieval
python scripts/run_benchmarks.py --category embedding
python scripts/run_benchmarks.py --category context

# Сравнить с предыдущим baseline
python scripts/run_benchmarks.py --compare tests/performance/latency_benchmarks.json

# Падать CI при регрессии >20 %
python scripts/run_benchmarks.py --compare baseline.json --fail-on-regression

# Через Makefile
make benchmark-baselines
make benchmark-compare
```

### Выходные файлы

| Файл                                         | Формат     | Назначение                              |
|----------------------------------------------|------------|-----------------------------------------|
| `tests/performance/latency_benchmarks.json`   | JSON       | Машино-читаемый для CI gates           |
| `tests/performance/latency_benchmarks.md`     | Markdown   | Человеко-читаемый отчёт                |

## Задержки компонентов

### 1. Операции эмбеддинга

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| Оценка токенов (короткий)       | ~50 токенов / 200 символов    | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| Оценка токенов (длинный)        | ~2500 токенов / 10 КБ         | <1,0     | <5,0     | <10,0    | 5,0 мс      |
| SHA-256 хэширование             | ~2,6 КБ строка                | <0,1     | <0,5     | <1,0     | 0,5 мс      |
| Попадание в кэш эмбеддингов     | кэш на 1000 элементов         | <0,01    | <0,1     | <0,2     | 0,1 мс      |
| Промах кэша эмбеддингов         | кэш на 1000 элементов         | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| Косинусное сходство             | векторы 1024-d                | <0,1     | <0,5     | <1,0     | 0,5 мс      |

**Ключевые наблюдения:**

- Оценка токенов через `tiktoken` — O(n) от длины текста; fallback `len(text)//4` — константное время.
- Кэш эмбеддингов использует двухуровневый поиск: точное хэш-сопоставление (O(1)), затем семантическое пересечение слов (O(n)).
- Косинусное сходство на векторах 1024-d — ~0,05 мс на современных CPU с NumPy.

### 2. Retrieval / Поиск

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| RRF-слияние (20 хитов)         | 2 × 20 ранжированных списков | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| RRF-слияние (50 хитов)         | 2 × 50 ранжированных списков | <0,5     | <2,0     | <4,0     | 2,0 мс      |
| Knee-point pruning             | 20 результатов                | <0,5     | <2,0     | <4,0     | 2,0 мс      |
| Score filtering                | 20 результатов                | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| In-memory cache get            | кэш на 1000 элементов         | <0,1     | <0,5     | <1,0     | 0,5 мс      |

**Ключевые наблюдения:**

- RRF-слияние — O(n+m), где n, m — размеры списков. С 50 хитами с каждой стороны остаётся <2 мс.
- Knee-point pruning использует векторизованные NumPy-операции; доминирует `np.argmax` по массиву расстояний.
- Score filtering — простое list comprehension с проверкой порога.

### 3. Реранжирование

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| ColBERT score (5×10)           | 5 query × 10 doc токенов, 64-d | <0,5     | <5,0     | <10,0    | 5,0 мс      |
| ColBERT score (20×50)          | 20 query × 50 doc токенов, 128-d | <5,0  | <50,0    | <100,0   | 50,0 мс     |
| Усечение текста                 | ~20 КБ вход                   | <0,1     | <0,5     | <1,0     | 0,5 мс      |
| Генерация ключа кэша           | ~80 символов каждый           | <0,1     | <0,5     | <1,0     | 0,5 мс      |

**Ключевые наблюдения:**

- ColBERT late interaction — O(q_tokens × d_tokens) на документ. Тест 20×50 на 128-d — верхняя ожидаемая граница числа токенов.
- Усечение текста — O(1); простой slice строки в `max_tokens * 4` символов.
- Cross-encoder задержка здесь **не** тестируется (требует загруженной модели). Ожидайте 150–400 мс на батч 20 пар `ms-marco-MiniLM-L-6-v2` на CPU.

### 4. Сборка контекста

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| Chunk hash (SHA-256)           | ~500 символов                 | <0,1     | <0,5     | <1,0     | 0,5 мс      |
| Дедупликация (10 чанков)       | 10 пар (chunk, score)         | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| Дедупликация (50 чанков)       | 50 пар                        | <0,5     | <5,0     | <10,0    | 5,0 мс      |
| Дедупликация (200 чанков)      | 200 пар                       | <2,0     | <20,0    | <40,0    | 20,0 мс     |
| Build (5 чанков)               | 5 чанков, 4К бюджет токенов   | <0,5     | <5,0     | <10,0    | 5,0 мс      |
| Build (20 чанков)              | 20 чанков, 16К бюджет токенов | <2,0     | <20,0    | <40,0    | 20,0 мс     |
| Реордер                        | 10 чанков                     | <0,1     | <1,0     | <2,0     | 1,0 мс      |
| Подготовка контекста (полная)  | 15 чанков, dedup + build      | <5,0     | <30,0    | <60,0    | 30,0 мс     |

**Ключевые наблюдения:**

- Дедупликация — O(n) с SHA-256 на чанк. На 200 чанках — ~10–20 мс.
- Сборка итерирует чанки и оценивает токены; доминирует конкатенация строк.
- `prepare_context` — полный пайплайн: dedup → version resolve → group → build. Лучший индикатор реальной задержки.

### 5. Граф / Multi-hop

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| Multi-hop BFS (2 hop)          | 5 старт. сущностей, 20 всего  | <1,0     | <10,0    | <20,0    | 10,0 мс     |
| Генерация Cypher               | 4 запроса                     | <0,1     | <0,5     | <1,0     | 0,5 мс      |
| Global search (20 саммари)     | 20 сообществ, по 100 слов     | <0,5     | <5,0     | <10,0    | 5,0 мс      |

**Ключевые наблюдения:**

- BFS обход ограничен `max_hops` × `max_results_per_hop`. На 2 hop и 10 результатах в худшем случае ~200 path explorations.
- Генерация Cypher — простое string pattern matching, ничтожная задержка.
- Global search делает keyword overlap scoring по всем community-саммари.

### 6. Скоринг и эвристики

| Бенчмарк                       | Размер входа                  | p50 (мс) | p95 (мс) | p99 (мс) | Порог (p95) |
|--------------------------------|-------------------------------|----------|----------|----------|-------------|
| Time decay (20 чанков)         | 20 чанков с timestamp         | <0,5     | <5,0     | <10,0    | 5,0 мс      |
| Dynamic top-k                  | 3 запроса                     | <1,0     | <10,0    | <20,0    | 10,0 мс     |

**Ключевые наблюдения:**

- Time decay — `exp(-age_days / decay_days)` на чанк, O(n) операций.
- Dynamic top-k вызывает SLM для оценки сложности (когда доступен); fallback — эвристика на основе количества слов.

Эти бенчмарки измеряют полный FastAPI-пайплайн с замоканными внешними сервисами (Qdrant, LLM, Redis). Они изолируют **накладные расходы фреймворка** от задержки сервисов.

|-----------------------------------|-------|----------|----------|----------|-------------|

| `/v1/models`                       | GET   | <20      | <500     | <800     | 500 мс      |

**Заметка:** С реальными сервисами добавьте:

| Сервис                              | Ожидаемая задержка         | Заметки                                  |
|--------------------------------------|---------------------------|------------------------------------------|
| Qdrant dense search                  | 5–30 мс                   | Зависит от размера коллекции и HNSW    |

| Redis cache lookup                  | <1 мс                     | Включая сетевой RTT                    |

**Ожидаемая полная E2E (реальные сервисы, CPU):**

| Сценарий                                       | p50     | p95     |
|------------------------------------------------|---------|---------|

## Детекция регрессий

### Интеграция с CI

```yaml
# .github/workflows/benchmark.yml
- name: Run latency benchmarks
  run: |
    python scripts/run_benchmarks.py \
      --compare tests/performance/latency_benchmarks.json \
      --fail-on-regression

- name: Upload benchmark report
  uses: actions/upload-artifact@v4
  with:
    name: benchmark-report
    path: tests/performance/latency_benchmarks.*
```

### Пороги регрессии

| Severity    | p95 Delta | Действие                                      |
|-------------|-----------|-----------------------------------------------|
| OK          | <10 %     | Без действий                                  |
| Warning     | 10–20 %   | Исследовать в PR review                       |
| Regression  | >20 %     | Заблокировать merge, нужно исправить          |
| Critical    | >50 %     | Немедленно откатить                            |

### Обновление baselines

После улучшений (новый кэш, оптимизация алгоритма):

```bash
# Запустить и сохранить новый baseline
python scripts/run_benchmarks.py --output tests/performance
git add tests/performance/latency_benchmarks.json
git commit -m "perf: update latency baselines"
```

## Рекомендации по тюнингу

### Применённые оптимизации (v2.0)

| Оптимизация                                       | Компонент                      | Эффект                                            |
|---------------------------------------------------|--------------------------------|---------------------------------------------------|
| Параллельный dense+sparse эмбеддинг               | `hybrid_search`                | Снижает задержку эмбеддинга ~40 % через ThreadPoolExecutor |
| Инкрементальный rerank-кэш                        | `rerank_chunks`                | Пересчитывает только некэшированные пары          |
| Кэш эмбеддингов запросов                           | `TwoStageReranker.fast_score`  | Устраняет повторное кодирование запросов            |
| Pre-computed word index                          | `GlobalSearch.search`          | O(N*M) → O(1) word lookups через инвертированный индекс |
| Кэш эмбеддингов документов                         | `TwoStageReranker.fast_score`  | Переиспользует документы между вызовами rerank     |
| LRU биндинг кэша                                  | `EmbeddingCache.__len__`       | Включает мониторинг памяти и eviction             |

### Если эмбеддинг-кэш >0,1 мс

- Уменьшите `EmbeddingCache.max_size` (по умолчанию: 1000)
- Переключитесь с FIFO на LRU
- Рассмотрите Redis для shared cache

### Если RRF-слияние >2 мс для 50 хитов

- Пре-сортируйте входные списки (уже отсортированы от Qdrant)
- Используйте NumPy-векторизованный RRF
- Рассмотрите снижение `top_k` с 50 до 30

### Если ColBERT >50 мс для 20×50

- Уменьшите размерность токенов (64-d vs 128-d)
- Пре-фильтруйте документы с bi-encoder
- Запускайте ColBERT на GPU

### Если дедупликация >20 мс для 200 чанков

- Добавьте Bloom-фильтр для exact-hash матчей
- Снизьте `top_k` retrieval
- Set-based dedup по усечённому тексту (первые 200 символов)

### Если сборка контекста >30 мс для 15 чанков

- Пре-вычисляйте chunk-хэши при индексации
- Уменьшите размер метаданных в заголовках контекста
- String builder pattern вместо конкатенации

### Если обход графа >10 мс для 2 hop

- Ограничьте entity-map connectivity (max 10 соседей)
- Добавьте importance scoring для отсечения путей
- Кэшируйте результаты обхода для повторяющихся сущностей

## 10. Результаты нагрузочных тестов

Эти бенчмарки измеряют систему под устойчивой конкурентной нагрузкой через asyncio-симуляцию (aiohttp). Результаты фиксируются в `tests/performance/test_load.py` и пишутся в `tests/performance/load_test_report.json`.

### 10.1 Симуляция конкурентных пользователей

| Симуляция          | Конкурентных пользователей | Цель                                   | Утверждение             |
|--------------------|---------------------------|----------------------------------------|------------------------|
| **Light Load**     | 10                        | Измерить p50/p95/p99                   | Error rate < 50 %       |
| **Moderate Load**  | 50                        | Измерить RPS, ошибки, перцентили       | Error rate < 50 %       |
| **Heavy Load**     | 100                       | Стресс-тест — сервис должен выживать | p95 < 60 с, errors < 80 % |

### 10.2 Перцентили времени отклика

| Load Level | p50 (мс) | p95 (мс) | p99 (мс) | Error Rate |
|------------|----------|----------|----------|------------|
| 10 users   | varies by service latency | — | — | < 50 % |
| 50 users   | —        | —        | —        | < 50 % |
| 100 users  | —        | —        | —        | < 80 % |

**Заметка:** Реальные значения задержки зависят от сервисов (LLM, Qdrant, эмбеддер). С замоканными сервисами (TestClient) все перцентили ожидаются < 5 с. С реальными — применяются суммарные значения из §End-to-End.

### 10.3 Генерация отчёта

```bash
# Нагрузочные тесты против live-сервиса
```

- Per-simulation breakdown: concurrent_users, successful_requests, errors, elapsed_seconds
- Перцентили задержки: p50_ms, p95_ms, p99_ms
