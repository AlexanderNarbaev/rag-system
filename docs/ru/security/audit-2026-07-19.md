> **Область.** Аудит первой линии RAG-прокси: аутентификация, ограничение

## 2. Критические проблемы

Набор тестов аудита сам по себе не внёс новых проблем с CVSS ≥ 7. Были
обнаружены две **существующие** слабости, оформленные как `xfail`-кейсы,
чтобы пробел оставался видимым до выхода исправления.

1. **История сообщений не ограничена** — `proxy/app/api/chat.py`
   `ChatCompletionRequest.messages` не имеет ограничения `max_length`.
   Злонамеренный клиент может отправить тысячи прошлых сообщений, раздувая
   контекстное окно LLM. Отслеживается тестом `test_very_deep_message_history_is_truncated`
   (`xfail`). Митигация: добавить `Field(..., max_length=100)` в `ChatMessage`
   или валидатор модели.
2. **Инъекция в LDAP DN** — `proxy/app/auth/ldap.py` `_build_user_dn`
   выполняет прямой `str.replace` для `{username}`. Имя пользователя, содержащее
   `,`, `=`, `\` или NUL, позволяет манипулировать DN. Отслеживается тестом
   `test_ldap_injection_in_user_search_is_escaped` (`xfail`). Митигация:
   экранировать `username` по RFC 4514 (например, `ldap3.utils.conv.escape_rdn`).

## 3. Рекомендации

1. **Подключить новые тесты к CI.** Добавить `tests/security/` в корень
   сбора `pytest` и запускать `make test-security` (или эквивалент) как
   обязательный гейт наряду с `make lint` / `make typecheck`.
2. **Запускать сканер зависимостей еженощно.** Запланировать
   `scripts/security_audit.sh` в CI; убедиться, что `pip-audit` установлен в
   раннере. Ронять сборку при регрессиях `pip-audit --strict`.
3. **Довести два `xfail`-результата до закрытия.** Открыть issues для
   ограничения истории сообщений и экранирования LDAP DN; убрать маркеры
   `xfail` после исправления продакшн-кода.
4. **Ротировать JWT-секрет по расписанию.** `proxy/app/shared/config.py`
   автоматически генерирует эфемерный секрет, если он не задан — это
   инвалидирует все токены при перезапуске. Продакшн-развёртывания должны
   задавать `JWT_SECRET` через менеджер секретов и ротировать его ежеквартально.
5. **Ужесточить бюджет rate-limit для `/v1/auth/login`.** Поток
   неудачных логинов всё ещё остаётся поверхностью брутфорса; существующий
   `RateLimitMiddleware` помогает, но рекомендуется выделенный более строгий
   бюджет для `/v1/auth/login`.

| Фреймворк                                              | Статус     | Доказательства                                                                                          |
|--------------------------------------------------------|------------|---------------------------------------------------------------------------------------------------------|
| **GDPR — ст. 32 (безопасность обработки)**             | ✅ Достаточно | Ожидается TLS-терминатор на ingress; аутентификация + rate limiting на месте; секреты в env, не в логах. |
| **GDPR — ст. 25 (защита данных по замыслу)**           | ⚠️ Частично | `InputValidator.sanitize_for_log` маскирует email и IP. Добавить явное редактирование PII в полезных нагрузках `Messages`. |
| **SOC 2 — CC6.1 логический доступ**                    | ✅ Достаточно | RBAC + ACL-фильтр + rate limit на пользователя; задокументировано в `docs/en/guides/access-control-rbac.md`. |
| **SOC 2 — CC6.6 управление уязвимостями**              | ⚠️ Ручная   | `scripts/security_audit.sh` существует; ещё не запланирован.                                            |
| **SOC 2 — CC7.2 мониторинг**                           | ✅ Достаточно | `proxy/app/shared/audit.py` логирует все события администрирования/обратной связи.                      |
| **ISO 27001 — A.9.4.1 ограничение доступа к информации** | ✅ Достаточно | ACL на уровне чанков + обход администратором покрыты `test_acl_penetration.py`.                        |
| **OWASP ASVS V2 (аутентификация)**                     | ✅ Достаточно | bcrypt + JWT exp + отзыв refresh-токенов проверены.                                                     |
